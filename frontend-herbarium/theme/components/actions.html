Actions

An action changes your garden. It is drawn as a filled stake so it can never be mistaken for a way of getting somewhere, and it stays where you left it — nothing moves because you tapped it.

Stable v1.0.0

Overview

Use an action for anything that writes: watering a plant, filing a scan, renaming a nickname, deleting a bed. An action changes something you own, offers you the way back, and leaves you standing where you were.

Do not use an action to go somewhere. A destination is an edge, drawn as a ruled line with its arrow already showing — see Edges. The two vocabularies are deliberately unalike: you should be able to tell a change from a journey by shape alone, before you touch either.

This page also owns the fields an action submits — text, select, notes, switch, segmented control. A field without an action beside it is a form you cannot finish, so they are documented together.

Rule of thumb

If a tap changes your garden, it is an action. If it changes where you are, it is an edge.

The primary action

Use one primary action per view — the thing you came to do. A second filled action of the same weight makes you read both to find out which one the screen is about.

Name the change, not the mechanism. Water Fern says what will be true afterwards; Submit says only that something happened. Keep the plant's nickname in the label when the view holds more than one plant.

Variants

Five weights, and each one means something. Pick by what the change does, never by how much attention you would like it to get.

VariantClassUse it for
Primary hbm-act--primary The one change this view exists for. Filled in the accent, one per view.
Grow hbm-act--grow Something joins your garden — a plant added, a scan kept, a bed created.
Default hbm-act An ordinary change sitting beside others: rename, re-scan, mark done.
Quiet hbm-act--quiet Declining or dismissing. It is a real change, so it is still an action, not an edge.
Danger hbm-act--danger A change that removes something. Never the primary action of a view.

Sizes and shapes

Three modifiers adjust an action's footprint without changing its meaning. Combine them with any variant.

An action reads only semantic roles. Never reach past them to a colour primitive, and never pick a padding or a radius that is not on the scale.

Behaviour

An action has four states you can see — rest, hover, focus and disabled — and one it enters after it fires.

Disabled

Disable an action only when the change is genuinely unavailable, and say why beside it. A disabled action with no explanation reads as a fault in the app.

The change offers its own undo

A completed change becomes its own way back for a few seconds, in place. Add data-hbm-undo with the past-tense label and data-hbm-undo-seconds with the window; the system wires the countdown on page load. Nothing scrolls, nothing opens, and the camera does not move — the button you pressed is where the reversal is.

When a change is worth confirming somewhere you can see from anywhere, raise an arrival instead of a banner. An arrival names where it came from, so you are never told about a change without being told where it landed.

herbarium.toast("Watered Fern", { tone: "positive", origin: "Garden", actionLabel: "Undo" });

Extra changes in a menu

An action that opens a menu holds only more actions. Never put a destination in one — a menu is a shelf of changes, and travelling from inside it leaves you unable to say where you came from.

Keyboard

Every action is a real <button>, so Tab reaches it and Enter or Space fires it. Inside a menu, Escape closes and puts focus back on the trigger. The switch and the segmented control below take Enter or Space too. Do not add key handlers of your own; the ones the system wires are the whole contract.

Reduced motion

Under prefers-reduced-motion the durations collapse in the tokens, so an action's fill and border change without a visible transition, and the menu opens without unfurling. Nothing an action tells you is carried by movement — the countdown is text, the state is colour and border. See Motion.

Fields and inputs

A field is where you type what the action will save. Every field carries a visible label; a placeholder is an example, never the label, because it disappears exactly when you need it.

When a field is wrong

Say what to do next, not what went wrong. Mark the control with aria-invalid and point its aria-describedby at the message, so the correction is read out with the field rather than found later.

Switch and segmented control

A switch is a change that takes effect as you flip it — there is no save. A segmented control chooses between a few named options that are all visible at once; if there are more than four, use a select.

Actions on an uncertain claim

When the system is unsure, the action next to the claim must not be. Keep the hedge on the claim and let the action stay plainly worded, so agreeing or correcting is a choice you make with the doubt in front of you. The full pattern lives in Uncertainty.

Accessibility

Every action is a native <button type="button">. Never build one from a div or a link: a link that changes your garden is announced as a destination, and someone using a screen reader will be told they are about to travel when they are about to water a plant.

Contrast and focus

The label and fill of each variant are paired roles, so contrast holds in both the paper and dusk themes; do not re-colour an action with a token of your own choosing. The focus ring comes from the base :focus-visible rule and is never removed or narrowed — it is the only thing a keyboard user has to see where they are.

Names

An icon-only action carries aria-label naming the change and its subject — Rename Fern, not Edit. Where a longer name helps but would crowd the label, add it with the .hbm-visually-hidden utility rather than a title attribute.

Keyboard path

Tab reaches every action in the order it is written, so write the primary action last in a footer and first in a row where it is the point. A menu returns focus to its trigger on Escape. A disabled action stays out of the tab order, which is why its reason must be readable beside it rather than on hover.

What is announced

The arrival rail is a polite live region, so a change confirmed by herbarium.toast is read out without interrupting. A field's error is tied to its control by aria-describedby and is read as part of the field. The switch reports its own state through aria-checked, and each segmented option through aria-pressed — keep those attributes truthful, because they are what a screen reader reads instead of the colour.

Usage guidance

Do
Monstera

Draw navigation as an edge and mutation as a filled action, so the two are told apart by form before either is activated.

Don't

Give a destination and a mutation the same form — the user cannot tell what will change their garden.

Do

Keep one primary action and let the alternative sit quietly beside it, so the view says plainly what it is for.

Don't

Fill two competing actions at the same weight — the choice has to be read twice before it can be made.

Do

Name what a destructive change removes, so nobody presses it to find out.

Don't

Label a removal with the mechanism alone — the label has to say what leaves your garden.

Two more rules that have no rendered counterexample worth showing. Write labels in sentence case and in PlantPal's own words — due today, my garden, needs attention; the wording rules are in Voice & copy. And never place an action so that using it scrolls, re-orders or re-lays-out what is around it: a change updates in place, and the entries it writes appear in the Care log where they belong. The principle behind both is the six principles.
