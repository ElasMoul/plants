# Herbarium — authoring contract

Every page in this documentation site is written against this file. It is a
contract, not advice: follow it exactly. If a page needs something this
contract does not allow, the page is wrong, not the contract.

System name: **Herbarium**. Component prefix: `hbm-`. Docs prefix: `ds-`.
Version: **1.0.0**.

---

## 1. Ground rules

1. **Never modify anything under `assets/`.** `tokens.css`, `system.css`,
   `docs.css`, `system.js`, `docs.js` and this file are frozen for the life
   of v1.0.0. Pages consume them. If you believe a component is missing,
   write the page without it and note the gap in your report — do not add a
   class, a token, or a NAV entry.
2. **Use only classes that already exist.** Product components come from
   `assets/system.css` (`hbm-` prefix); page scaffolding comes from
   `assets/docs.css` (`ds-` prefix). Read both files before writing a page.
   Do not invent class names, and never mix the two vocabularies: a docs
   layout element never gets an `hbm-` class, and a demonstrated component
   never gets a `ds-` class.
3. **Never write a raw colour, size, font or duration value.** Anywhere —
   demo markup, page-scoped CSS, inline styles. Every value comes from a
   token. Two rules, and they differ:
   - **Colour is semantic only.** Never name a colour primitive
     (`--hbm-leaf-400`, `--hbm-terra-300`…) in a page. Use the layer-2 role
     (`--hbm-text-secondary`, `--hbm-accent`, `--hbm-health-watch`…). The
     one exception is a `.ds-swatch` inside a colour specimen table, whose
     whole purpose is to show the primitive — see section 4.2.
   - **Geometry — space, size, radius, rule, lift, duration, easing — uses
     the scale directly** (`--hbm-space-5`, `--hbm-radius-sheet`,
     `--hbm-dur-2`), exactly as `system.css` does. These scales *are* the
     sanctioned layer; there is no second naming on top of them, and a
     value off the scale is not allowed.

   A page-scoped `<style>` block is a last resort for one-off illustrative
   diagrams only, never for a component.
4. **Escape every code sample.** Inside `<pre><code>`, `<` becomes `&lt;`
   and `&` becomes `&amp;`. Unescaped markup in a code block is the single
   most common authoring bug in this site — check twice before finishing.
5. **The markup in a specimen's `<details>` must match its preview exactly**,
   character for character apart from the escaping.
6. **Voice.** Second person, calm, specific, jargon-free — PlantPal speaks
   to a beginner gardener holding a phone next to their plant. State rules
   as rules ("Use one primary action per view"), never as suggestions.
   Explain *why* in one sentence when a rule is non-obvious. Sentence case
   in headings ("Plant tag", not "Plant Tag"). No exclamation marks, no
   marketing language, no alarm. When the system is unsure, the copy says
   so plainly — that is a feature of this product, not a hedge to hide.
   All product examples use PlantPal's own domestic vocabulary: *my garden*,
   *nickname*, *due today*, *needs attention*, *recent scans*. Latin
   binomials appear only in `.hbm-binomial`, never as something a user must
   know or type.
7. **Every page must be correct under RTL.** Use logical properties in any
   page-scoped CSS (`margin-inline-start`, never `margin-left`). Never
   hard-code a direction arrow in prose; the components draw their own.

## 2. Page skeleton

Every page uses this exact skeleton. Replace the UPPERCASE placeholders and
nothing else. The sidebar, the on-page table of contents and the footer are
generated by `docs.js` — never hand-write them.

**Path depth matters.** For a page inside `foundations/`, `components/`,
`patterns/` or `guidelines/`: `data-root="../"` and asset hrefs begin with
`../assets/`. For a page at the site root (`index.html`): `data-root=""`
and asset hrefs begin with `assets/`.

```html
<!DOCTYPE html>
<html lang="en" data-theme="light">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>PAGE TITLE · Herbarium</title>
  <meta name="description" content="ONE-SENTENCE PAGE DESCRIPTION">
  <link rel="stylesheet" href="../assets/tokens.css">
  <link rel="stylesheet" href="../assets/system.css">
  <link rel="stylesheet" href="../assets/docs.css">
</head>
<body data-page="PAGE_ID" data-root="../">
  <a class="skip-link" href="#main">Skip to content</a>
  <div class="ds-shell">
    <main id="main" class="ds-main">
      <div class="ds-article">

        <header class="ds-page-header">
          <p class="ds-kicker">GROUP NAME</p>
          <h1>PAGE TITLE</h1>
          <p class="ds-lede">ONE OR TWO SENTENCES SAYING WHAT THIS PAGE IS FOR.</p>
          <div class="ds-page-header__meta">
            <span class="hbm-badge hbm-badge--positive"><span class="hbm-dot"></span>Stable</span>
            <span class="hbm-badge hbm-badge--outline">v1.0.0</span>
          </div>
        </header>

        <section class="ds-section">
          <h2>SECTION HEADING</h2>
          <p>…</p>
        </section>

      </div>
    </main>
  </div>
  <script src="../assets/system.js"></script>
  <script src="../assets/docs.js"></script>
</body>
</html>
```

The stylesheet order is fixed: `tokens.css`, then `system.css`, then
`docs.css`. The script order is fixed: `system.js`, then `docs.js`.

`data-page` must be the page id already registered in the `NAV` array in
`docs.js`. Do not invent an id, and do not add one — every page this build
will produce is already listed there. Read `docs.js` to find yours.

write descriptive, scannable `h2`s.

## 3. Page arc

Every page follows the same order:

1. **Header** — kicker, `h1`, lede, status badges (in the skeleton above).
2. **Overview** — what this is, when to use it, when not to.
3. **The substance** — specimens, anatomy, variants, token tables.
4. **Behaviour** (component pages) — states, keyboard interaction,
   what happens under `prefers-reduced-motion`.
5. **Accessibility** — a dedicated `h2` on every component and foundation
   page: contrast, ARIA, keyboard path, screen-reader announcement.
6. **Usage guidance** — at least one Do/Don't pair.

## 4. Canonical content blocks

Use these four blocks. They are the only sanctioned shapes for their
purposes.

### 4.1 Live-demo specimen

A working component, its caption, and its exact markup.

```html
<figure class="ds-specimen">
  <div class="ds-specimen__preview">
    <button type="button" class="hbm-act hbm-act--primary">Water Fern</button>
  </div>
  <figcaption class="ds-specimen__caption">One primary action per view — the thing you came to do.</figcaption>
  <details class="ds-specimen__code">
    <summary>HTML</summary>
    <pre><code>&lt;button type="button" class="hbm-act hbm-act--primary"&gt;Water Fern&lt;/button&gt;</code></pre>
  </details>
</figure>
```

Preview modifiers: `ds-specimen__preview--stack` for full-width stacked
examples (sheets, tags, logs), `--center` for a lone centred item,
`--world` for an `.hbm-world` demo that must fill the frame edge to edge.

For screen-reader-only text use the `.hbm-visually-hidden` utility from
`system.css` — never a hand-rolled clip style.

Interactive demos are wired automatically by `system.js` on page load. To
raise a toast from a demo, call `herbarium.toast("Watered Fern", { tone:
"positive", origin: "Garden", actionLabel: "Undo" })`.

### 4.2 Token table

```html
<div class="ds-table-scroll">
  <table class="hbm-table">
    <thead>
      <tr><th>Token</th><th>Value</th><th>Use</th></tr>
    </thead>
    <tbody>
      <tr>
        <td><code>--hbm-accent</code></td>
        <td><span class="ds-swatch" style="background: var(--hbm-terra-500)"></span> <code>terra-500</code></td>
        <td>The resident's own voice — primary actions, active edges.</td>
      </tr>
    </tbody>
  </table>
</div>
```

The `style` attribute on `.ds-swatch` is the one sanctioned inline style in
this site, and it must reference a token — never a hex value.

### 4.3 Do / Don't pair

```html
<div class="ds-dodont">
  <div class="ds-dodont__panel ds-dodont__panel--do">
    <span class="ds-dodont__tag">Do</span>
    <div class="ds-dodont__demo">
      <a class="hbm-nav" href="#">Monstera</a>
      <button type="button" class="hbm-act hbm-act--primary">Log watering</button>
    </div>
    <p>Draw navigation as an edge and mutation as a filled action, so the two are told apart by form before either is activated.</p>
  </div>
  <div class="ds-dodont__panel ds-dodont__panel--dont">
    <span class="ds-dodont__tag">Don't</span>
    <div class="ds-dodont__demo">
      <button type="button" class="hbm-act hbm-act--primary">Monstera</button>
      <button type="button" class="hbm-act hbm-act--primary">Log watering</button>
    </div>
    <p>Give a destination and a mutation the same form — the user cannot tell what will change their garden.</p>
  </div>
</div>
```

Each panel gets exactly one sentence. Both panels must show a real,
rendered example, never a description of one.

### 4.4 Standalone code block

For CSS, JS or markup shown outside a specimen.

```html
<div class="ds-code">
  <pre><code>.my-page-demo { color: var(--hbm-text-secondary); }</code></pre>
</div>
```

## 5. Rules the components already encode

Do not undo these in a page. If a demo appears to need one of them broken,
the demo is wrong.

- **Edges before clicks.** Anything that navigates is `.hbm-nav` or
  `.hbm-edge-row`. Anything that mutates is `.hbm-act`. Never style one to
  look like the other, and never put a traversal inside a `.hbm-drawer`.
- **One focal point.** An `.hbm-world` has exactly one `.hbm-node--focus`,
  and only a user action moves the camera.
- **Position is persisted, never simulated.** Nodes carry `data-hbm-x` /
  `data-hbm-y` and `data-hbm-neighbours`. Use the same coordinates every
  time you demonstrate the same graph, so two loads lay out identically.
  Never write a demo that randomises or animates layout.
- **Non-structural change moves nothing.** A count, a status or a new photo
  updates in place.
- **Unknown is not empty.** Use `.hbm-node--unknown` /
  `.hbm-unknown-region` for regions that have not loaded, and
  `.hbm-empty-world` only for a place that genuinely has nothing in it.
- **Failure lives inside the node.** Use `.hbm-node-error` with its retry
  in place; never a page-level error banner.
- **Say when unsure.** Any demonstrated identification or diagnosis carries
  `.hbm-confidence`, and a low-confidence example uses `.hbm-hedge`.
- **Motion travels.** Nothing in a demo may fade, pop or teleport; the
  system's transitions already handle this, so do not add your own
  animation.

## 6. Finishing checklist

Verify every line before you finish a page.

- [ ] Skeleton matches section 2 exactly (skip link, `ds-shell`, `ds-main`,
      `ds-article`), and nothing is added outside `.ds-article`.
- [ ] `data-page` matches an id in `docs.js`'s `NAV`; `data-root` and every
      asset path match this file's actual depth.
- [ ] Stylesheets in order tokens → system → docs; scripts system → docs.
- [ ] Nothing under `assets/` was modified.
- [ ] Every class used exists in `system.css` or `docs.css`.
- [ ] No raw colour, size, font or duration value anywhere on the page, and
      no colour primitive outside a `.ds-swatch` in a colour specimen table.
- [ ] All `<pre><code>` content is escaped, and matches its preview exactly.
- [ ] Exactly one `h1`; `h2` for sections, `h3` for subsections; no skips.
- [ ] An Accessibility section exists (component and foundation pages).
- [ ] At least one Do/Don't pair.
- [ ] At least one live specimen with its code.
- [ ] Every interactive demo works with no console errors.
- [ ] The page reads correctly in both themes — toggle paper/dusk and look.
- [ ] Page-scoped CSS, if any, uses logical properties and is RTL-correct.
- [ ] Every internal link resolves to a path listed in section 2.1, with the
      correct relative depth. No invented slugs. This check is fatal.
