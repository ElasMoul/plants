Guidelines

Extending this system

How Rhizome changes without losing what it settled. This page says who owns which file, what a later round may add, what it may not touch without a ruling, how an addition is recorded so the next round inherits it, and how a version of this system is cut.

What this is

Rhizome exists because the same interface was re-taught to every new agent. The last system PlantPal shipped froze its assets/ the day it was written: nothing downstream could be fixed from inside, so every theme round copied the raw values, invented its own semantic layer, and re-derived the same rules from rejection notes. This page is the escape from that. assets/ is versioned, not frozen. You may extend it — under a name, in the register, in one direction only.

Everything Rhizome knows lives in five records, and each has exactly one owner. If you are about to change something, find it in this table first; the row tells you whether you are writing, amending, or asking.

Who owns what
RecordHoldsChanged by
constitution.json The C-register, the laws, the numbers, the page manifest, the amendment register. The owner, for invariants and parameters. A round, for the amendment register only — appending its own entry.
layout-determinism.json, traversal-map.json, degradation-spec.json Placement, routes and states, each with its own verification block. A round may add a node, an edge or a state to them. The verification block is not editable.
assets/tokens.css The raw layer, the semantic layer, the palettes, the mirrored --rz-param-* numbers. A round, by adding — under a named amendment. Never by removing or re-keying.
assets/system.css, assets/system.js The classes a theme fills, and the primitives that make the laws performable. A round, by adding a primitive under a named amendment, when a law cannot otherwise be run.
This documentation site Each law, stated once, on the page that owns it. Any round, freely — but a law is written on one page and cited from the rest.

The shortest version: add beside, never over. A token you add is new vocabulary the next round inherits. A token you re-key is a promise broken in every page and every theme that already read it, and there is no way for them to find out.

The laws

Law 1 · constitution.json → amendments.register

Nothing enters assets/ unrecorded. If you added a token family, a class or a primitive, there is an entry carrying its id, the round that added it, what it adds, why the existing vocabulary could not carry the meaning, and which files changed.

Diff assets/ against the previous version and collect every added --rz- token name and every added .rz- or .doc- selector. Each one appears in the adds array of exactly one register entry, and every entry names files that actually differ.

Law 2 · constitution.json → parameters

The declared numbers — the 4 and the 2 of the density rule, the 300ms, the lattice pitch and origin, the zoom clamp, the 10-second slow threshold — are single-sourced in the constitution and mirrored into the token layer and the script. A round does not edit them, and never writes one of them as a literal.

Load any page and call RZ.verifyParameters(). It returns []: the computed --rz-param-* values and RZ.PARAMS agree with the constitution. Then grep the round's own CSS and JS for those numbers as bare literals — nothing is found outside the three mirrors.

Law 3 · C12, C14

A theme round chooses the key, the type voice and the drawing density. It does not choose the mechanism. You may set a different hue for a kind, drop the display rung an octave, or tighten the card's air; you may not make the four ranks read as three, and you may not give mutation and traversal one form.

Run the two blur tests against the round's own build. Freeze a frame, blur the plane, and count the card widths — four remain distinguishable and each head graduation is still separable by length. Then mask every affordance's text: each is a filled stake or an outlined chip with a caret, and no third form exists outside the camera cluster.

Law 4 · C6

An addition that would make this surface a different regime is not an amendment; it is a new mission. Rhizome is judged by the atlas law and by no other. A round that flattens the veins into a hierarchy, or replaces a hop with a route, has left the system rather than extended it.

On the round's build, assert the edge list still contains cross-branch edges — a journal entry joined to the plant it is about, two problems sharing one treatment course — and that edge count is at least node count. Then hop ten times and assert location.href never changed.

Law 5 · constitution.json → amendments.policy

A semantic token is never removed and never re-keyed. The set of names in assets/tokens.css only grows. If an existing name is wrong for what you mean, that is the evidence you need a new one beside it — not a reason to redefine the old one under everything already reading it.

Collect every --rz- name declared in this version's tokens.css and every name in the round's. The first set is a subset of the second. For each shared name, the meaning stated in its layer comment is unchanged; a new value in a new palette is expected, a new meaning under an old name is the defect this law names.

Specimens

What "the key is yours" actually means

Press one. Every colour on this page — the article, the sidebar, the card below, the drifting field behind it — is a token reference, so one attribute on the root re-keys all of it at once, with no save step. This is the whole surface a theme round is meant to work on, and it is wired by the system rather than by this page.

A new palette is the cheapest legal extension in this system: a block of values under a new [data-palette] key, re-keying every token the semantic layer already declares. It needs no amendment entry at all, because it adds no vocabulary — it only fills the vocabulary that is there. Everything that does add vocabulary needs the next section.

How to make an amendment

Four steps, in this order. If you cannot write step 3 in a sentence that names a real gap, you do not have an amendment — you have a preference, and the class you want probably exists.

  1. Look for it first. Search assets/system.css and assets/docs.css for the meaning, not the name you had in mind. Most gaps are vocabulary misses.
  2. Add it in the right layer, with the prefix. A product token or class is --rz- / .rz-; a documentation-site class is .doc-. A semantic token references a raw one; it never carries a literal value.
  3. Record it in constitution.json → amendments.register, using amendments.entry_shape.
  4. Say so on your page, in one sentence, where the thing you added is used.
{
  "id": "A2",
  "round": "<round or batch that added it>",
  "adds": ["--rz-kind-tool", "--rz-kind-tool-wash"],
  "reason": "Why the existing vocabulary could not carry the meaning —
              named as a gap, not as a taste.",
  "files": ["assets/tokens.css"]
}
The entry, field by field
FieldWhat goes in itWhy it is there
id A and the next free number. So a page can cite the amendment the way it cites an invariant.
round The round or batch, and the page that needed it. The next reader can find the thing that motivated it and see whether it still needs it.
adds Every token name or selector, exactly as declared. This is the array Law 1's diff is checked against.
reason The gap, and what you tried that did not carry it. Half of all amendments are refuted by writing this field honestly. The rest earn their place with it.
files Each file you touched. An entry whose files do not differ is a record of something that did not happen.

What needs an owner ruling

Three things are outside a round's reach, and each is outside it for the same reason: a later reader has no way to tell a considered change from an accident, and every one of these has already been lost once.

Reach
ChangeWhoWhat happens if a round does it anyway
Adding a palette, a token family, a class, a primitive Any round, under a named amendment Nothing — this is the intended path. Record it and move on.
Adding a node, an edge or a state to the three sibling specs Any round Nothing, as long as the spec's own verification block still passes unedited.
Changing a declared parameter Owner ruling RZ.verifyParameters() stops returning [], and the CSS and the script begin to disagree about the same number.
Removing or re-keying a semantic token Owner ruling Every page and every theme already reading that name is silently wrong, with nothing to catch it.
Editing, adding to, or reinterpreting the C-register Owner ruling The citations on every page stop resolving, which is exactly the condition this system was built to end.

A ruling is not a formality and not a blocked road. If you believe a parameter is wrong — the density threshold, the travel timing, the pitch — write the case down with the evidence from your own build and hand it over. What you may not do is change it quietly and leave the next round to discover that the number in the CSS and the number in the script are two different opinions.

Cutting a version

This system is and lives in a folder named for it. A version is cut, not edited in place.

  • A patch is documentation only: a clearer sentence, a better specimen, a fixed link. No file under assets/ moved.
  • A minor version carries amendments: things were added, the register grew, and everything that read the old version still reads correctly.
  • A major version is the only place a semantic token may be re-keyed or a parameter changed, and only with the ruling that authorised it recorded beside it.

The name stays Rhizome and the slug stays plantpal-cae942ee. A second system for this app is not a version of this one; it is a decision to stop inheriting, and it costs what it cost last time.

Writing a page in this system

The authoring contract for pages is assets/AUTHORING.md, and it holds the page skeleton, the canonical blocks and the finishing checklist. Two of its rules are the ones rounds actually break, so they are worth repeating as consequences rather than as instructions.

The first is state a law once. A law lives on the page the constitution says carries it, and every other page cites and links. The density rule belongs to aggregate and spacing; explaining it a second time on a node page produces two wordings, and the round after that has to work out which one is the system.

The second is a law that cannot be checked is a preference. Every law block on every page carries a verification a reader can actually run — a diff, a count, an assertion, a blur. That is the whole difference between this system and a style guide, and it is why the rules of this page are themselves written as checks.

Accessibility

Extending a system is where accessibility is usually lost, because the thing added is judged on how it looks and not on what it does. The behaviour side of this ground is owned by accessibility; what follows is what an addition owes it.

  • Anything added that carries meaning by colour carries it in a word too. A new kind gets its name in .rz-n__kind, a new state gets a sentence in the card's own words. Turn the screen greyscale: nothing added has gone missing.
  • A new affordance takes one of the two forms. A stake changes your garden, a chip travels, and inside chrome both become a leading mark. An addition that invents a third form has broken the one thing a user can rely on before clicking.
  • A new way to arrive announces itself. If your addition can change the focus, it goes through RZ.go() — which writes the arrival sentence and moves the world view's label in lockstep with the visible you-are-here. A hop performed by hand is a hop nobody hears.
  • Anything added that is reachable by pointer is reachable by keyboard, following the graph. Arrow keys pick the neighbour that actually lies that way; a direction with no vein is spoken rather than ignored.
  • New CSS uses logical properties. inline-start, block-end, margin-inline — never left and right. A physical property added today is a page pointing the wrong way in RTL tomorrow, and it will be found by a user rather than by a reviewer.
  • An addition respects reduced motion. If it animates, it has a held, drawn form under data-motion="reduced" that still carries direction — not an abrupt swap, and not nothing.

Do and don't

Do

Add --rz-kind-tool beside the eight kinds that exist, record it as A2 with the gap it names, and say so in one sentence on the page that uses it. The round after you inherits a ninth kind and knows why it is there.

Don't

Point --rz-kind-guide at the colour you wanted instead. Every page, specimen and theme already reading that name silently changes meaning, and nothing in the build can tell.

Do

Read the density threshold as RZ.PARAMS.density.threshold and var(--rz-param-density-threshold), so the CSS and the script cannot drift and RZ.verifyParameters() can prove it.

Don't

Write 4 into your own component because it happens to be four today. The number is declared once in the constitution, and a copy of it is a second opinion waiting to be wrong.

Do

Take a whole new key — hue, type pitch, card air — and argue about that. It is what a theme round is for, and Law 3's two blur tests tell you immediately whether you have stayed inside the system.

Don't

Copy the raw values into a new file and build a parallel semantic layer beside this one. That is how the last system ended up with 105 duplicated values and 125 invented tokens, and it is the failure Rhizome exists to prevent.

Do

Cite a C-number and link to constitution.json, quoting the statement as written.

Don't

Paraphrase an invariant into a second wording on your page. Two wordings of one law is how a register becomes a rumour, and the round after yours will re-derive it from rejection notes (C6).

Where else this appears

The blur test for rank and the four card widths belong to node and typography. The two forms are owned by action rail, navigate to and iconography, and the register they change into inside chrome by chrome. The kind channel and the live palette mechanism this page extends are on colors. The density rule and the numbers behind it are owned by aggregate and spacing; the one travel timing by traversal and motion. The states an addition must survive are on degradation, and the behaviour an addition owes a keyboard and a screen reader on accessibility.
